# UI設計と次段階

## 画面

上段の左をプレビュー、右をファイルと保存先に割り当てた。再生とモード切替はプレビュー直下に置いた。右欄は元動画と完成予定時間を常時表示し、詳細、保存先、空き容量を個別に開ける。仕切りをドラッグすると幅と高さを変えられる。

下段は上から、操作ボタン、選択した項目の操作、タイムライン。ボタンには「残す範囲」「ブランク」「停止」のように効果を短く書いた。緑の「残す」区間と薄色の「削除」区間を対応させ、効果は短いラベル付きのマーカーで示した。開始と終了の調整は別ボタンにし、フレーム番号を横に表示した。

テロップは段番号が大きいほど前に表示し、同じ段の前後関係は選択時のボタンで変更する。開始・終了は採用映像のテロップバーの両端、または編集画面で変更する。ブランクと停止のバーは挿入位置を示し、その中での時刻は編集画面で指定する。

## 時間とプロジェクト

- タイムラインの横座標は元動画のフレーム番号を基準にする。変更するのは利用者が拡大・縮小したときだけ。
- TimeMap は採用範囲を速度の境界と停止位置で分け、ブランクと停止を挿入して完成時刻を計算する。再生時に完成時刻から元動画のフレームを求める。挿入中の再生カーソルは元動画上のアンカーに留まる。
- 範囲の終了は内部では含まない。操作画面で最後のフレームを指定する際は「含む」と表示する。
- .kirihari 形式 v1 は、元動画のフレームレートの分子・分母、任意の PTS 境界配列、採用・挿入・速度の ID、テロップ参照先と範囲、相対パスを持つ。テロップの映像位置は採用区間の生成時の基準フレームからの差として保持するため、前方を切っても映像との対応を維持する。
- 挿入時間の秒とフレームの換算には試作の出力基準として素材の fps を使う。将来は確定した出力 fps で量子化する。
- 削除した参照先に付いていたテロップは警告付きで保持し、別の映像に自動で移さない。Undo で復元できる。

## 技術選定

**WPF / C# / .NET Framework 4.8 以降**を採用した。Windows の標準機能を使えるため、追加ランタイムを ZIP に入れずに試作できる。WPF の描画、ファイルダイアログ、動画プレビューを組み合わせ、時間変換と JSON を UI から分離した。弱点は Windows 専用の画面実装と、素材再生が OS コーデックに依存すること。Android では画面を作り直し、同じプロジェクト形式と時間変換テストを共有する。

Tauri 2 と Web UI は、UI 資産を共有しやすい候補。Windows では WebView2 が必要で、Evergreen が入っていない端末への対応や、Fixed Version 同梱時の容量・更新方法を検討する必要がある。試作では WPF を使い、Android 着手時に別の UI 実装と再比較する。[WebView2 の配布方式](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

## 自己評価

| 観点 | 評価 |
| --- | --- |
| 最初の操作 | 起動と同時に架空映像が出て、カット段のドラッグ方法が下に表示される。動画を選ぶ入口も常に見える。初見利用者による評価は次段階。 |
| 残す場所と消す場所 | 色と「残す」「削除」の文字で区別できる。短いバーでは文字が省略されるため拡大が役立つ。 |
| 微調整と効果 | 通常と1フレームが画面に表示され、選択境界も示す。速度区間が短い場合やマーカーが近接する場合は拡大が必要。 |
| テロップ | 位置を映像上で動かせる。区間内の時刻入力は初心者には難しく、再生位置から表示開始・終了を採る操作を次回の評価候補にする。 |
| 元動画と完成予定 | 再生モードに加えて二つの時刻を表示する。ブランクでは元動画の時刻欄を空欄にして対応がないことを示す。 |
| 小画面 | 1366×768・125%相当でも主要ボタンを表示できる。情報の展開や拡大時はスクロールが必要で、上下の仕切りで映像と編集欄の面積を調整できる。 |
| ボタン数 | 効果とテロップの入口は常時表示し、詳細操作は選択時に限った。境界ループやズームの利用頻度は利用者評価で確認する。 |

## 次の段階

1. 利用者が架空素材で A〜E の手順を試す。初見でカットを始められるか、ブランクと停止を区別できるか、テロップの表示時刻を設定できるかを確認する。
2. UI の修正後、Windows の解像度・実際の DPI・低性能 PC・各コーデックで試す。機密素材の前に、通信、OS 履歴、ファイル参照、キャッシュを監査する。
3. UI 承認後に、デコーダのフレームインデックスと PTS、プロキシ対応、実フレームのプレビュー、MP4 書き出し、画質と音声を実装する。プレビューと出力を共通の時間マップで検証する。
4. 実際に配布するバイナリのライセンス、対応ソース、配布条件、署名方針を整理してから公開の可否を確認する。Android では SAF・USB・バックアップ除外・ストレージ制約を別途検証する。
