# 初回起動から2回目までの実画面検証

2026年11月7日、Windows x64上で実施。GitHubへの作成・push・タグ送信・Release公開は行っていない。

## 最終版での再確認

PDFメニュー・5つの編集支援機能・AI導入対応の追加後、最終EXE（SHA-256 `5f4c7fac24075f032281e949597fad34709a1f4fb73a7e3fa890927ee2a565c6`）でも次を確認した。

1. 最終本体ZIPをWindows PowerShell 5.1のinstall.ps1で新しい検証フォルダに導入。全同梱ファイルがZIPと一致し、完了記録・FFmpeg設定がない状態で開始した。
2. 通常のEXEを起動し、初回準備画面でFFmpeg不足・開始ボタン無効を確認。「必要な部品を準備」から約109 MBを実ダウンロードし、FFmpeg 9.0.2の配置と「準備完了」を確認した。
3. 「KIRIHARIを始める」を押し、編集画面・プロジェクト選択画面を確認して正常終了した。
4. 同じEXEの2回目起動で、準備画面を経由せず編集画面へ進むことを確認。完了記録の更新時刻は初回のまま、FFmpegの配置は1つ、EXEのハッシュも同じだった。2回目も正常終了した。

起動と画面操作はComputer Useで行い、完了記録やFFmpeg設定を手動で作成していない。.NET FrameworkとWebView2は既存の導入済み環境を使用したため、これらの未導入PCでの実インストールは引き続き未検証。

証跡は `.tooling/final-install/evidence`（初回・準備完了・編集画面・2回目のアクセシビリティ情報、開始前・初回完了時のJSONと結果）。これはローカル検証用で配布しない。以下は、追加機能開発前の検証記録として保持する。

## 確認した流れ

| 操作 | 実際の結果 |
| --- | --- |
| 本体ZIPを新しいフォルダに展開 | 初回準備の完了記録・FFmpeg設定・本体内のFFmpegがない状態で開始。 |
| KIRIHARI.exeを通常起動 | 「はじめの準備」を表示。.NET Framework・WebView2は準備済み、FFmpegは不足と表示。開始ボタンは無効。 |
| 「必要な部品を準備」を押す | Gyan提供のGitHubミラーから約109 MBのZIPを実ダウンロード。固定SHA-256を確認し、FFmpegをアプリ内へ配置した。 |
| 導入完了 | FFmpegも「準備できています」となり、開始ボタンが有効になった。この時点ではまだ初回準備の完了記録は作成されていない。 |
| 「KIRIHARIを始める」を押す | 完了記録 `data/setup-v1.txt` とツールの場所を保存。WebView2の編集画面とプロジェクト選択画面が開いた。 |
| アプリを終了 | ウィンドウがなくなったことを確認。 |
| 同じEXEを2回目として起動 | 準備画面を経由せず、編集画面とプロジェクト選択画面が開いた。 |
| 保存状態を確認 | 完了記録の更新時刻は初回のまま。FFmpegの配置は1つで、再取得されていない。 |
| 2回目を終了 | 正常に終了した。 |

起動・ボタン操作・終了・再起動はComputer Useで行った。検証中に状態を偽装する設定や初回完了ファイルの手動作成は行っていない。配布ZIPと同じEXEを使い、検証前後のSHA-256は一致した。

この記録は下記ハッシュの時点のセットアップ検証である。その後のPDFメニュー・Undo/Redo等の追加によって現在の配布EXEのハッシュは変わっている。追加後の検証範囲はverification.mdに記載し、この初回実ダウンロードの証跡と区別する。

## 環境と確認範囲

- .NET Framework：Release値534296。4.8以降の条件を満たす導入済み環境。
- WebView2 Runtime：156.0.4314.58。導入済み。
- 自動取得したFFmpeg / FFprobe：9.0.2。実行してバージョンを確認。
- 導入済みのMicrosoftの部品は再インストールせず、既存環境を保った。
- FFmpegが他アプリ固有のフォルダから見つかる処理は削除し、本体内・PATH・利用者の指定先で探すようにした。

今回は「不足したFFmpegを実導入し、導入済みのMicrosoftの部品はそのまま使う」経路を確認した。.NET 4.8未満、WebView2未導入のPCでの実インストール完了やOS再起動の検証は含まない。
